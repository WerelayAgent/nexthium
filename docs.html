What Nexthium does

Nexthium is an MCP server for Robinhood Chain. Any client that speaks the Model Context Protocol connects to a single URL and receives 50 tools. With them the AI reads live chain state, simulates and explains transactions with risk checks, prepares unsigned transactions, and builds, compiles and verifies contracts.

Nexthium holds no keys and signs nothing. Each tool that changes state hands back an unsigned transaction with an approval link. The person opens the link, sees a new simulation and signs in their own wallet.

  • Open access. The URL answers without an account or a key, up to 120 calls a minute.
  • Mainnet first. Every tool works on chain 4663. Pass chainId: 46630 to reach the development network.
  • Stored encrypted. A prepared transaction lives for 24 hours as ciphertext, and its key travels inside the approval link. Nexthium builds and simulates each transaction itself, so Nexthium sees what it contains.

First connection

Register the server in your client, ask something about Robinhood Chain, and approve a transaction only when you choose to act.

In Claude or ChatGPT, open the connector settings, add a custom connector and paste this same URL.

Try it

  1. 01Type which block is Robinhood Chain on right now? The AI calls get_network_info and replies with live data.
  2. 02Type show the balances of 0x… The AI calls get_wallet_info.
  3. 03Type prepare a 0.01 ETH transfer from 0x… to 0x… The AI calls prepare_token_transfer and hands you an approval link.
  4. 04Open the link, read the simulation and approve in your wallet. The AI then calls wait_for_transaction and reports the outcome.

Switching chains

Calls go to mainnet unless you say otherwise. Add chainId: 46630 to any call to run it on the development network.

Rate limits

Anyone can call Nexthium. Each caller has a budget counted over a rolling 60-second window.

CallerCalls per minuteHeavy per minuteCounted by
Open access12010A salted one-way hash of the caller's network address
Agent key60060The key itself

Heavy calls compile Solidity or submit source for verification: check_token_risk, prove_token_risk, trace_funds, list_token_approvals, compile_contract, prepare_contract_deployment, verify_contract, get_stock_token, get_stock_playbook, ask_chain. Each heavy call draws on both budgets.

Past the budget, a call returns rate_limited at once. Retry when the window rolls forward, which takes 60 seconds at most.

Agent keys

An agent key is optional and belongs to a wallet. Make one on the Agent keys page and send it with each request:

  • Your wallet signs a one-time message to prove it controls the address. Signing sends no transaction. The message stays valid for five minutes and works once.
  • Nexthium trades the signature for a management token that lasts 30 minutes. That token manages keys and has no access to tools.
  • Each wallet can keep five active keys.
  • Nexthium shows the key one time and keeps only its SHA-256 hash and a 12-character prefix. Save it right away; a lost key is replaced with a new one.
  • A header that is present yet malformed, unknown or revoked gets unauthorized. Open access applies only to requests that send no header at all.

A key may hold a name, a description of up to 500 characters and a capability list. Mark the profile public and those three fields appear in the agent directory. The key, its hash and its owner wallet stay private.

Read tools

Read tools take no wallet and change no state. They query the RPC node, and Blockscout for history and verified source.

  • get_wallet_info gives the ETH balance, the nonce, whether code lives at the address, and the ERC-20 tokens it holds.
  • get_transaction_history lists the 25 most recent transactions for an address.
  • get_contract_info reports bytecode size, verification state and the ABI, plus the verified source on request.
  • read_contract runs a view or pure function with the verified ABI, or with an ABI you pass in.
  • get_event_logs covers the latest 5,000 blocks unless told otherwise, up to 50,000, and decodes events for verified contracts.

Amounts travel as decimal strings in base units, since a JSON number cannot carry a 256-bit integer. Tools that accept a human amount, prepare_token_transfer among them, state it in their description.

Simulation and risk flags

simulate_transaction executes a transaction on top of the latest block through eth_simulateV1. You get success or the revert reason, gas used, the sender's expected balance changes, risk flags and a plain-language summary. Every prepare_* tool runs this same preview and returns it with the transaction.

Risk flags come from fixed local rules applied to the decoded call, the simulation result and the target contract. They catch unlimited or long-lived approvals across ERC-20, Permit2 and operators, zero-address recipients, and targets that are unverified or cannot be decoded.

FlagSeverityWhat it signals
insufficient-fundsdangerThe sender's balance is short of value plus gas, so the transaction would revert.
simulation-faileddangerThe simulated run reverted. The flag message includes the revert reason.
simulation-unavailablewarningThe simulator returned no result at this moment. Prepare the transaction again for a fresh preview.
zero-addressdangerSends to the zero address, where value is lost.
unlimited-approvaldangerAn approval at or close to the maximum amount. Nexthium prepares exact approvals only.
approval-for-alldangerHands an operator control of every NFT the owner holds in a collection.
approvalwarningLets a spender move a set token amount.
token-to-contractwarningTokens sent to a contract that may have no way to move them onward.
unverified-contractwarningBlockscout holds no verified source for the target contract.
undecoded-callwarningNo known ABI decodes the call data sent to this contract.
data-to-eoawarningCall data addressed to an account that holds no code.
verification-unknowninfoBlockscout gave no answer, so the verification status is unknown.
contract-creationinfoA contract deployment. The deploying wallet becomes its owner.

A simulation reflects the chain at a single point, and state keeps moving. The approval page runs the simulation once more in your browser right before you sign.

Prepare tools

Prepare tools assemble an unsigned transaction, set its nonce and gas, attach a preview and return an approval link. Signing and sending stay with you.

  • Sender required. Every call needs from. The AI asks the user for a wallet address and Nexthium uses exactly that one.
  • Exact approvals. prepare_token_approval approves the amount you give it, and 0 revokes. Every approval Nexthium prepares carries a set amount.
  • Ordered batches. prepare_batch accepts up to ten steps with consecutive nonces. The approval page sends each step once the one before it confirms.
  • Short encrypted links. The result holds unsignedTransactions, previews and signUrl. The link opens an encrypted copy that expires after 24 hours, and anyone holding the full link can open it.

Approval links

An approval link looks like /sign#<id>.<key>. Nexthium stores the transaction encrypted under the id for 24 hours. The key sits in the fragment after the #, which browsers keep on the device; the page fetches the stored copy by id and decrypts it locally. Nexthium creates and simulates the transaction, so Nexthium knows its contents; the encryption guards the stored copy. The approval page opens only links Nexthium stored this way.

  1. 01The page decodes the payload and checks it strictly: version, chain ID, one to ten steps, valid addresses and hex. It rejects a malformed link. Compare the details your wallet shows with what you expect before you approve.
  2. 02Connect the wallet given in from. The page asks the wallet to change network when needed.
  3. 03Every step runs through simulation again on current state and appears with its risk flags.
  4. 04Approve in your wallet. The page waits for the receipt and shows confirmed or reverted.

Signing on your own side

An agent or backend with its own key can sign directly. Take unsignedTransactions, sign locally, pass the raw hex to send_signed_transaction, then pass the hash to wait_for_transaction. Nexthium checks the chain ID of the signed transaction before it broadcasts, and reports success once a receipt confirms it.

Uniswap v4 swaps

Nexthium routes swaps through Uniswap v4 on Robinhood Chain and picks the best route it finds.

  • Name a token as ETH, a symbol like USDG, or the token's contract address. Pass amount in whole units, such as "0.5".
  • Selling ETH needs one signature. The first sale of a given token adds an approval step.
  • Each quote lists the output, the minimum you accept at the default 1% slippage, and the Nexthium fee.
  • A token becomes swappable once it has a Uniswap pool holding liquidity.

Swap fee

Nexthium keeps a service fee of at most 1% of the swap output, taken inside the same transaction. Every amount you see already accounts for it, and the fee applies only to swaps that complete.

Approvals

An approval lets a contract move your tokens without asking again. They pile up and are rarely removed, so Nexthium lists them and prepares the revoke.

  • list_token_approvals finds the ERC-20 allowances, Uniswap Permit2 allowances and NFT operator approvals a wallet has granted. The history only says where to look: every item is checked against the chain now, so one that was already spent or revoked does not appear.
  • Each item is rated info, warning or danger. A plain wallet as spender, or an unlimited amount to an unverified contract, is danger. An unlimited amount to a verified contract is warning. When the wallet holds none of the token, the level drops a step because nothing is exposed today, and atRisk shows how much is.
  • prepare_revoke_approvals prepares up to 10 revokes with consecutive nonces. Pass the items from the list, or leave them out to revoke the riskiest ones. An approval that is already gone is skipped. Each revoke is one transaction and costs a little gas.

A very long approval history is searched for as long as the call allows. When it stops early, the result says complete: false.

Rug Prover

prove_token_risk answers one question about a token: can whoever controls it stop a holder from getting their money out? It does not guess from function names. It runs each power the controller has and measures what happens to a holder. The /autopsy page runs the same check from a token address. Nothing is signed or sent.

  1. 01Read the code. Collects the function selectors in the token's bytecode, and in its implementation when it is a proxy, and matches them against known privileged functions: fee and tax changes, blocking wallets, pausing, transaction limits, minting and upgrades. This works on contracts with no verified source.
  2. 02Find the controller. Reads owner(), then getOwner(), then the EIP-1967 admin slot, and falls back to the deployer. Ownership at the zero address counts as renounced.
  3. 03Prove each power. In one simulated block, a throwaway account buys 0.002 ETH of the token on Uniswap v4, the controller calls the power with the harshest arguments the contract accepts, and the account sells. The sell is compared with the same block without the controller's call.
GradeMeaning
provenThe sell reverts, or returns less than half of a normal sell.
partialThe sell returns between half and 90% of normal.
not-effectiveThe controller's call reverts, or the sell is about the same.
unknownNo controller was found, or the simulation could not run.
not-simulatedUpgrades: the controller can replace the code, which cannot be tested without inventing the new code.

The verdict is trap when a sell already fails or any power is proven, risky when a power is partial or the controller keeps an untested power such as an upgrade, clean-so-far when nothing hurt the holder, and cannot-test when the token has no Uniswap v4 route from ETH. A token is traded in its own ETH pool, the one with the most liquidity; a launchpad pool with a hook counts once Nexthium has read that hook's verified source. A launchpad token that has not graduated yet is traded on its bonding curve instead. The report names the pool or curve it used. Every report lists what was not checked, including role-based access and trading outside Uniswap v4. Reports are kept for five minutes.

Money Trail

trace_funds follows money one hop at a time. Give it an address and a direction: in lists who sent it ETH and ERC-20 tokens, out lists where it sent them. The /trail page draws the result as a graph you can keep expanding by clicking a node.

  • Transfers are grouped per counterparty and asset, with the total, the number of transfers, the first and last block, and up to five transaction hashes. The 15 largest groups are returned.
  • Each hop reads up to three pages of history in that direction. truncated: true means older flows were not read.
  • The result also lists contracts the address created, and any Rug Prover verdicts already on record for addresses in the hop.
  • The page marks patterns in the graph it has loaded: an address that created three or more contracts, a token Rug Prover proved a trap, an address the explorer marks as a scam, one address that first funded three or more others with ETH, and five or more senders followed by one outgoing flow of at least 80% of what came in.

The graph holds up to 40 addresses. Hops are kept for ten minutes.

Stock Token Lens

Many tokens on Robinhood Chain reuse a stock's ticker and even the words "Robinhood Token". Nexthium counts a token as official only by its contract: it was created by Robinhood's StockFactory, or its beacon is Robinhood's or Ondo's. The /stocks page lists every official token and reports on one at a time.

  • list_stock_tokens lists the official tokens with ticker, company, address and issuer. Filter with query.
  • get_stock_token takes a ticker or an address. A copy comes back as impostor with the reason and the real token. An official token comes back with a report.
  • A ticker in a swap, such as "buy TSLA", resolves only to the official token.
Report fieldSource

Reference priceThe Blockscout explorer's exchange rate

Chain Pulse

get_chain_pulse returns what just happened on mainnet, newest first. Pass the returned cursor as since to get only newer events. The /pulse page polls the same feed every ten seconds.

KindWhat it is
new_poolA Uniswap v4 pool was created, with both currencies, the fee and any hooks
whale_transferA USDG or WETH transfer worth $25,000 or more; hops of one transaction count once
stock_eventA balance multiplier change, pause or oracle pause on an official stock token
activity_spikeThe newest blocks carry at least twice the day's average transactions per second

Events are kept for 24 hours. Titles come from token contracts, which anyone can name, so treat them as data. Native ETH transfers are not watched. When the explorer does not answer for a source, the result says which one in notes.

Lighter perps

Lighter runs the perpetual markets on mainnet. Nexthium covers market data, account data and deposit preparation. Orders are placed, changed and cancelled on Lighter with your own keys.

  • get_perp_markets gives price, 24-hour change, volume, open interest, maximum leverage and funding, with an optional symbol filter.
  • get_perp_account gives a wallet's USDG collateral, available margin and open positions, or exists: false.
  • prepare_perp_deposit prepares an exact USDG approval followed by the deposit, and stops when the wallet holds too little USDG.

Lighter's own terms exclude the United States, the United Kingdom, Canada, Switzerland, the United Arab Emirates and Singapore.

Privacy Pools

get_privacy_pool_info reads 0xbow Privacy Pools on mainnet: pool status, supported assets (ETH and USDG) and shielded balances. You deposit and withdraw in the official Privacy Pools app, and deposit secrets stay entirely inside that app.

Error codes

Over MCP, an error arrives as code: message with isError: true. Over HTTP, it arrives in the error envelope with the status listed here.

CodeStatusWhen it happens
invalid_input400An argument did not pass validation. The message names it.
unauthorized401The agent key is malformed, unknown or revoked, or the management token has expired.
forbidden403The key is valid and lacks the scope or chain this tool requires.
not_found404No such transaction, contract, tool or route exists.
rate_limited429The per-minute budget is used up. Retry within 60 seconds or add an agent key.
unsupported501This chain or provider has no support for the call, such as perps on the development network.
upstream_error502The RPC node, the explorer or a protocol API returned an error. Try the call again.
not_configured503The operator of this instance has yet to set up the provider the tool uses.

Common fixes

Connected, yet the tool list is empty

Make sure the URL ends with /api/mcp and the client uses the HTTP transport. With a key, check that it holds at least one scope; a key scoped to read lists read tools only.

Each call fails with unauthorized

The Authorization header carries something other than a valid key. Drop the header to use open access, or make a new key.

A prepare call reports insufficient funds

The preview ran on Robinhood Chain and the sender lacks value plus gas there. Top up the wallet, or pass the other chain ID (4663 or 46630) if you meant that chain.

The approval page finds no valid transaction

The link arrived cut short or edited. Some chat apps drop everything after the #. Ask the AI to prepare the transaction again and open the complete link.

The status stays pending

wait_for_transaction waits up to 60 seconds before it returns pending. Call it again with the same hash to keep waiting.

Contract details are missing

Blockscout supplies history, ABIs and verification status. While it is unreachable, reads that rely on it return upstream_error and the risk list includes verification-unknown.
